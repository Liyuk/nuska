# 衡量长任务的真正交付

状态：评测方案草案 · 2026-10-29；没有已运行的结果或排名。

## 评测对象

从一个强目标出发，系统独立推进并阶段性交付；用户在看到新信息后可以补充上下文或改变目标。评测系统最终是否满足**最新授权目标**、是否真实交付、质量如何，以及中途是否给出可用成果。对任务不可行的场景，正确说明原因及已完成内容也应单独评价，不算成功完成。

## 指标与判定

| 指标 | 定义 | 如何核验 |
| --- | --- | --- |
| 验证完成率 | 在可验收的任务里，产物满足全部必要条件的运行数 / 有效运行数 | 预先编写的独立检查与人工验收；同时列出分子分母 |
| 交付完整度 | 必需交付项中真实存在且通过各自检查的比例 | 产物清单及检查记录；不以文字声明代替产物 |
| 目的符合与质量 | 结果是否满足最新目标及其关键取舍 | 预先制定评分锚点；人工评价与理由，必要时双人复核 |
| 阶段成果可用性 | 中间成果能否独立审阅或用于决定后续方向 | 记录产物、交付时点、内容及阶段验收结果 |
| 错误完成声明 | 声称已完成但关键条件未满足的运行数 | 比较声明、外部状态与检查结果，保留证据 |
| 目标修订与恢复 | 新信息、纠偏、失败或中断后是否正确延续 | 对照修订时序、实际行动与最终交付 |
| 人工介入 | 用户主动催促、拆分、纠偏或接管的次数与性质 | 按预设分类记录；必要授权不等同于失败 |

不把模型自评当成唯一裁判；自动检查通过也不能自动证明复杂结果质量。对于开放任务，评分表应明确必要条件、质量等级和无法判断的情况。

## 初始任务集

- **研究交付**：给出明确问题，产出可追溯来源与结构化报告；中途补充影响结论的新资料。
- **工程交付**：在可控仓库完成一项功能并运行独立测试；中途变更一项业务约束。
- **有外部依赖的交付**：先产出可审阅的阶段结果，再在模拟服务或测试环境中处理一次失败和恢复。
- **不可完成的任务**：缺少必要权限或关键信息，检查是否准确报告阻塞、已有结果及下一步，而不是虚报成功。

每项任务预先固定成功条件、允许的权限、可用信息与检查方法；人工提供新信息的时机和内容也要预先记录。

## 对照与证据

相同任务、起点和可见权限下比较不同系统；模型和宿主均记录，模型选择差异单独报告，不将差异直接归因于 harness。保存任务版本、事件、实际产物、用户修订、检查日志与评审记录；敏感材料脱敏或本地保留。重复运行，报告样本量、无法判定和波动，不把少量结果当作普遍排名。

例如公开研究指出 coding-agent 评测中基础设施会影响结果，比较前需核查运行环境及波动：[Anthropic：Infrastructure noise in agentic coding evals](https://www.anthropic.com/research/infrastructure-noise)。该材料支持关注评测环境，并不证明本方案已验证。

## 公开基准：可以借鉴什么，缺什么

检索日期：2026-10-29。以下是公开资料的方案比较，不是 Nuska 的实测或对产品的排名。评测套件及评分方法会更新，实际运行应固定版本、任务集和环境。

| 公开基准与一手资料 | 可借鉴之处 | 对 Nuska 问题的边界 |
| --- | --- | --- |
| [SWE-bench](https://github.com/SWE-bench/SWE-bench) / [论文](https://arxiv.org/abs/2310.06770) | 从真实 GitHub issue 出发，以代码修改和测试评估问题解决；可借鉴可复现的仓库初态和独立测试。 | 主要针对软件 issue 的一次性结果；测试通过并不覆盖开放任务的目的符合、阶段交付、用户修订或任务接力。 |
| [OSWorld](https://github.com/xlang-ai/OSWorld) / [OSWorld 2.0 论文](https://arxiv.org/abs/2606.29537) | 真实桌面及网页环境中的跨应用工作流，2.0 特别关注长任务、动态环境和中途信息；可借鉴环境状态检查与长链路任务。 | 主要检验电脑操作工作流，无法单独证明多 Bot 协作、意图演化或用户对成果质量的满意度。版本不同不能直接比较分数。 |
| [SlopCodeBench 论文](https://arxiv.org/abs/2603.24755) | 让 Agent 随规格演化持续扩展自己先前的代码，既看检查点正确性，也研究代码结构变化；可借鉴多阶段延续和回归检查。 | 聚焦代码与静态规格变化，代码质量代理指标并不等于所有类型交付的质量；检查点也不自动代表对用户有用的阶段成果。 |
| [τ²-bench](https://github.com/sierra-research/tau2-bench) / [论文](https://arxiv.org/abs/2506.07982) | 用户和 Agent 在共享环境中协作，模拟用户并通过环境状态等评估结果；可借鉴受控的多轮输入、工具作用与状态验收。 | 客服领域和模拟用户有特定假设；不能用对话轮数或模拟结果直接推断真实用户愿望交付的体验。 |
| [CodeClash](https://github.com/codeclash-ai/codeclash) / [论文](https://arxiv.org/abs/2511.00839) | 以竞争目标、跨轮迭代衡量自主改进，提醒我们可检验目标结果而不限定每一步实现。 | 竞争环境、可计算的目标函数和持续优化不等价于真实用户任务的开放性与验收。 |
| [GAIA 论文](https://arxiv.org/abs/2311.12983) | 真实世界问题需要推理、浏览、多模态及工具使用，可用于参考多能力任务设计。 | 答案导向问题不能充分衡量长期产物、阶段性交付或可恢复的多 Agent 执行。 |

共同启示是：**最终验收、部分进度、产物质量及跨阶段延续必须分别记录**。上述基准各覆盖部分能力，不能用某一个榜单分数代替 Nuska 的交付指标。

## 把研究目标转成可执行协议

每个任务定义一个清楚的初始目的、一组必要验收条件和至少一个可审阅的阶段产物。用户修订采用预先安排的信息注入：说明触发事件、输入内容、允许系统看到的时间及更新后的判定条件；系统无需为了进入下一阶段反复询问。修订前已产出的阶段成果仍单独评价，不能用新目标抹去历史证据。

对于每次运行，记录 `(任务版本、目标修订序列、运行配置、阶段产物、最终产物、执行事件、外部状态、验收证据)`。必要条件逐条标记通过、失败或无法判定，展示分项而不只给平均分；最终完成必须满足全部必要条件。阶段成果按预设时点或触发事件检查其可用性，而不是把中间消息数量算成进度。

设置可复现的困难：派发未送达、工具报错、中断恢复、过时子任务迟到及目标调整。分别核查系统是否发现问题、是否合理恢复，以及是否把未完成工作说成完成。对确实缺少权限的任务，单独评分其阻塞说明和已完成产物；不能把诚实阻塞计入成功，也不将其与虚报等同。

比较多个系统时，先做同模型、同任务、同权限的受控对照以研究 harness 差异；也可另做各系统代表性配置的整体体验比较，但两种结论必须分开。多模型方案保留实际模型及配置记录。人工评审先写评分锚点，盲评时隐去系统身份；对开放质量项保留分歧和理由，并对独立检查器做已知正确及错误产物的校验。任何阶段尚未运行时，所有指标都只是方案，不能当作事实结论。
