# 交付式协作的最小实现设计：目标对象、验收出口与身份分层

状态：设计方案草案 · 2026-10-29。基于[能力盘点审阅](../landscape/2026-10-29-dsh-multi-bot-composition-review.md)、[归档证据](../community/ds-bot/2026-10-29-requirements-evidence.md)与[原语核验](../landscape/2026-10-29-dsh-primitives-verification.md)。**未实现、未运行**；下面所有"已有"都能指到源码或公开文档，"设计"都是候选方案。

## 问题与范围

要回答三个问题：

1. 在一套已经能跑的多 Bot 群聊之上，加什么最小结构，才谈得上"交付式协作"（目标被保住、结果被验收、未完成项被说明）？
2. 这些结构应该挂在哪一层，才不与现有机制打架？
3. Bot 的行为差异应该怎么分层，才不会退化成"起个名字、写段人设"？

不包含：模型选择与效果比较；产品 UI 设计；Grok Bot 内部机制的复刻。本文不假定 Nuska 已选定宿主或实现形态。

## 材料和方法

- 承载层源码：ds-bot `v0.2.3`（commit `4a7b550`），逐文件核对其群回合、工作树、记忆、续行与提示词组装。
- 底层原语：DSH `0.2.1-rc.2` 安装包，逐包核对 goal、plan mode、Team、workflow、schedule、作业、权限等，见[原语核验](../landscape/2026-10-29-dsh-primitives-verification.md)。
- 需求侧：作者公开提交的 discussion / issue 归档，共 22 篇，见[归档证据](../community/ds-bot/2026-10-29-requirements-evidence.md)。
- 方法：先列"已有能力"，再列"证据支持的缺口"，最后给最小改动。每条设计主张标注它复用的是哪个已有机制；没有对应机制的才标"新增"。

## 发现与证据

### 1 能力盘点：已经有什么，缺什么

| 能力 | 现状 | 位置 |
| --- | --- | --- |
| 长期 Bot 身份（名字、角色、instructions、模型、目录、权限） | 已有 | `ds-bot/roster.js` |
| 群回合（逐个发言、`@` 交接、`[PASS]`、未回复/停放通知） | 已有 | `ds-bot/groups.js` |
| Bot 之间私聊派活的树，结果自动上返，重启后继续等 | 已有 | `ds-bot/handoffs.js` |
| 三 scope 记忆 + 每次发言后的记忆复盘 | 已有 | `ds-bot/memory.js`、README「Memory」 |
| 跨上下文窗口续行（checkpoint / handoff note） | 已有 | `ds-bot/steward.js`、`parts.js` |
| 会话事件日志、fork、跨会话检索 | 已有（底层） | DSH session / query 包 |
| **结构化的目标对象与版本** | **缺**（只活在 checkpoint 的散文里） | — |
| **工作的验收状态与产物字段** | **缺**（work 只有 from/to/results） | — |
| **群派活的记录** | **缺**（`@` 不建 work；群消息只留最近 60 行） | — |
| **"已领取 / 已处理"的显式事件** | **缺**（DSH 全域只到 inbox 接受） | — |

这张表决定了下面设计的顺序：**先把已有机制接起来，再补字段，最后才考虑新机制。**

### 2 目标对象与版本

现在目标只以自然语言存在于交接 note 的 `Goals` 小节里。它的问题是：不可引用、不可比对、无法判断"这条旧结果还适不适用"。

设计（最小形态）：

```
goal {
  id, revision,              // 目标版本，用户每次改范围就 +1
  statement,                 // 用户原话 + 一句结构化概括
  done_when[],               // 可检查的完成条件，逐条
  out_of_scope[],            // 明确不做的事
  owner,                     // 谁对最终交付负责（一个人，不是角色名）
  updated_at, updated_by
}
```

三条约束：

- **权威源只有一个**。群 notice 可以放"当前版本的可读副本"，但它必须是从 goal 渲染出来的，不能反过来成为事实来源。
- **旧结果保留版本号**。目标升版后，已完成的工作标 `based_on: revision N`，是否仍然适用由 owner 判断，不由系统默认继承。
- **不引入第二套"继续"机制**。这个对象只是状态，不驱动轮次；轮次仍由现有会话续行负责。

### 3 "完成"必须经过工具，不能是一段文本

模型的"已完成"永远是主张。验收唯一能挂住的抓手是工具面——ds-bot 自己就是用工具面禁用 goal 的（`tools.js`），说明插件层可以注册和拦截工具。

设计：新增一个提交动作（名字待定，暂写 `deliver`），参数是结构化交付：

```
deliver {
  goal_revision,
  artifacts[],        // 路径或链接，逐项
  checks[],           // 跑过什么检查、结果是什么（命令 + 退出状态）
  unfinished[],       // 明确没做完的
  unknowns[],         // 外部副作用结果未知的
  next_step
}
```

四个判断：

- 它产生一条**记录**，不只是发一条消息；记录可以在群里看到。
- 它不阻止模型继续写"我做完了"这种话，但它让"有没有交过东西"成为可查事实。**验收的第一条不是禁止模型说话，而是让主张与记录不对等时可以指出。**
- 它必须允许"交付失败"和"交付未完成"。否则它会变成又一个逼模型美化结果的东西。
- 自动检查只覆盖机器可判的条件（文件存在、命令通过、引用可达）；目的符合度留给人和明确的评审记录。

### 4 复用已有判断，而不是再造一个评审者

ds-bot 的 steward 在每次换段前已经做了一次"逐项对照用户请求"的检查（提示词原文见[审阅](../landscape/2026-10-29-dsh-multi-bot-composition-review.md)第 3 节）。它现在只输出"换段还是压段"。

最小改动：让它顺带产出结构化结果，例如

```
{ action: "switch" | "compact",
  unfinished: [ {item, why} ],
  questions_waiting: [ ... ],
  basis: "..." }
```

理由：

- 零新增模型调用（这次判断本来就要发生）。
- 判断者与被判断者分离（它读对话，不参与生成）。
- 它的输出天然是"未完成项"，正是用户最需要看到的一段。

风险要写清：它是一次小模型调用，会误判；因此它的输出只能作为**提示和记录**，不能直接当作验收结论。

### 5 两处工作记录，不要只改一处

| 场景 | 现有 | 要补 |
| --- | --- | --- |
| Bot 之间私聊派活 | `works`：`{from, to, room?, parent?, open[], results[], at}` | `target_revision`、`deliverables[]`、`verify`（谁检查、结果） |
| 群里 `@Name` 派活 | 无记录；只有群消息最近 60 行 | 一条独立记录：`{from, to, room, opened_at, closed_at, deliverable, verify}`，且**不随 60 行窗口过期** |

状态模型（沿用已归档讨论里的提议，只补一个"结果未知"）：

```
待派发 → 已派发 → 已领取 → 进行中 → 已交付 → 待验收 → 已验收
                       ↘ 阻塞 / 失败 / 已取消 / 结果未知
```

两条语义要求：

- "已派发"只说明投递成功；"已领取"和"已处理"必须是独立事实。DSH 全域目前没有"已处理"语义，这是一项新增。
- 一个工作项只有一个 owner；owner 是任务字段，不是人格字段。

### 6 身份（persona）怎么分层才真正影响行为

先看实际注入点。Bot 的系统提示由这几段拼成（`ds-bot/prompt.js`）：

1. 身份段：`You are {name}… Your role: {role}` + 该 Bot 的 `instructions`；
2. `Shared behavior foundation`（9 条，全队相同）；
3. `How your Bot team works`（20 条，全队相同）；Main Bot 另加一段。

按源码字符数计，共享规则约 **9,200 字符**（1,756 + 7,407），Main Bot 再加 1,775；个体差异由一段 `instructions` 承担，通常比它短一个数量级。也就是说：**一个团队里 90% 的行为文本是同一份，个体差异只有一小段。**

再看另外三个注入点：群 notice 每轮随消息注入（`groups.js`）；记忆按 scope 进系统提示，且在会话分段时冻结；消息头带着这一轮的语境（`delivery.js`：reply / room / report / update / stopped / resumed / deferred）。

于是分层应当是：

| 层 | 载体 | 谁改 | 会不会变 | 该放什么 | 不该放什么 |
| --- | --- | --- | --- | --- | --- |
| L0 能力 | model、effort、权限预设、工作目录 | 人 | 少变 | 能力档与风险档 | 人设形容词 |
| L1 身份 | name + role + instructions（系统提示） | 人 / Main Bot | **不变，进缓存前缀** | 判断风格、专业领域、**绝不做什么** | 当前任务、成员名单、群状态 |
| L2 平台纪律 | 共享规则段 | 上游 | 全队相同 | 交付纪律、失败处理、证据要求 | 个别人的例外 |
| L3 场景 | 群 notice，每轮注入 | 群管理员 | **随时可改** | 本次目标与版本、交付判据、**谁收尾**、发言规则 | 长期偏好 |
| L4 记忆 | own / group / team 三个 scope | Bot / 管理员 | 换段生效 | 偏好、事实、用户决定 | 当前任务状态 |
| L5 工作 | 工作记录（不进提示） | 系统 | 事件驱动 | 目标版本、产物、验收、未完成项 | 人格描述 |
| L6 事件语境 | 消息头角色 | 系统 | 每轮 | — | — |

三条硬约束，决定"能不能这么放"：

1. **缓存约束**：`prompt.js` 的注释明确该段的文本只依赖渲染会话自己的 Bot 记录，目的是让前缀跨轮次、跨成员变化保持字节稳定（`interpolate: false`）。**所以 L1 不能放任何会变的内容**，否则整段前缀失效、缓存全丢。任务与责任只能放 L3 或 L5。
2. **可见范围约束**：群成员各有隐藏会话，群看不到 Bot 私聊；群记忆只在该群内可见。**因此跨群的角色一致性只能靠 L1**，不能靠记忆共享。
3. **责任归属约束**：收尾责任是任务属性，不是人格属性。写进 L1，每个 Bot 都会觉得自己应该收尾；放进 L5，"一个工作项只有一个 owner"才有结构保证。

由此得到一条可操作的规则：

> **L1 写"你是谁、怎么判断、绝不做什么"；L3 写"这一次要交出什么、谁收尾"；L5 记"这件事到哪了"。**

这条规则也解释了四种常见错法：

| 错法 | 现象 | 应该在哪层解决 |
| --- | --- | --- |
| 把职责写进两个字的 role 标签 | 两个角色的职责重叠时，章程、调度、人设三处对不上，且无处裁决 | L5 的任务归属 + L3 的收尾人 |
| 把调度当成角色属性 | 任务建在某个会话里，群维度看不到，执行者也不知道自己欠着什么 | L5，而不是 L1 |
| 把任务状态写进记忆 | "当前目标是 X" 进了长期记忆，目标改了旧值还留着 | L5 的版本 + 过期标记 |
| 所有 Bot 用同一套模板写 instructions | 个体差异只剩名字，行为上仍是同一个 Agent | L1 只写判断权限与禁区，L3 写本次责任 |

与已归档讨论的对应：公开帖里已经提出"全能模型下人设容易失去区分度"和"角色差异需要落到工具、权限或验收约束"（`657`），也提出"提示词不能替代权限"（`639`）。本节的增量是**层与载体的对应关系**，以及三条约束——尤其是缓存约束：它把"把职责写进人设"这个做法从"效果不好"变成"技术上不可行"。

### 7 优先级

| 级别 | 事项 | 为什么是这个顺序 |
| --- | --- | --- |
| P0 | 目标对象 + 版本 | 没有它，"旧结果是否适用"无法判断，后面的验收都悬空 |
| P0 | `deliver` 工具 + 记录 | 验收唯一能挂住的抓手；也是"主张 vs 事实"的分离点 |
| P1 | steward 输出结构化未完成项 | 复用已有模型调用，改动最小，收益直接 |
| P1 | 私聊 works 加字段 + 群派活独立记录 | 覆盖两种派活；只改一处会漏掉群场景 |
| P2 | 派发 / 领取 / 处理三事件分开 | 新增语义，工作量不能低估（底层完全没有） |
| P2 | 一个工作项一个 owner，且不是人格字段 | 让"谁收尾"有结构保证 |
| P2 | 失败与未知作为一类结果 | handoff 模板已有 `Blocked:`，但它没进交付物；外部副作用未知目前无记录位 |
| P3 | 先删减机制，再新增 | 现在同时有 goal 轮次、段续行、Ralph、workflow、Team 多种"继续"；再加一层会让碰撞更糟 |

### 8 实现路径

| 路径 | 能改到 | 拿不到 | 代价 |
| --- | --- | --- | --- |
| **A. fork ds-bot** | 工作记录、群回合、提示词组装、全部 7 层 | — | 跟随上游漂移；需要熟悉 35 个 host 模块的组织方式 |
| **B. 另写一个 DSH 插件** | 只有 DSH 层：工具、系统提示、会话事件 | 群、工作树、群回合都在 ds-bot 的 `state.json` 里，且无公开接口 | 低，但只能覆盖单会话 |
| **C. 用 DSH 原生 Team 自建群** | 任务板、依赖、claim、CAS、roster | 无群 UI、无长期身份、无三 scope 记忆 | 最高 |

判断：**交付语义必须和消息语义同层**。ack、迟到、未接、恢复、结果上返都在 ds-bot 里；换一层做，这些语义对不齐。因此 A 是唯一能一次做完整的路径；B 适合先在单会话验证 `deliver` 与验收记录；C 只在确认 Team 会长期维护时才值得。

另有一条改动更轻的路线：把第 3–5 节里要加的字段和工具作为**上游贡献**提出，因为它们本来就是这一层的产品方向。这不等于"不改 DSH"那条自律被破坏——自律约束的是 DSH，不是应用层。

## 局限和未解问题

- 全部是静态设计，没有实现；`deliver` 的字段是否够用、会不会变成形式主义，只能靠实验回答。
- 目标对象的权威源放哪（工作树扩展字段 / 独立文件 / 会话日志投影）未定；三者的恢复语义不同。
- steward 的输出能不能稳定复现，未测；它是小模型调用，可能有随机性。
- "已处理"语义要新增到什么程度，还没想清：是所有工具调用都记，还是只记对外派发。
- 群记录不再随 60 行滚动，会改变数据增长速度，需要和现有存储/备份策略一起看。
- fork 与上游贡献的取舍取决于维护者意愿，本报告不预设。

## 对 Nuska 的意义

这套设计给 Nuska 提供了一个具体的起点，而不是再画一层架构：**交付式协作的第一件事不是"更强的 Agent"，而是"可引用的目标 + 可检查的交付记录 + 明确的分层"。** 这三点都不需要换模型，也不需要更大的上下文窗口。

同时它给出一个可迁移的判断：在任何宿主上做同类能力，先问三件事——目标是否存在为可引用对象；完成是否存在为工具面的事实；责任是否存在为任务字段而不是人格描述。这三个问题比"支持几个 Agent"更能区分系统。

## 下一步

最小闭环实验（不改代码也能先做一版）：

1. 选一个真实群任务：用户给明确目标，管理员拆两路独立资料方向，交一份带来源的报告。
2. 只用现有机制埋点：目标与判据写进群 notice（L3）；私聊派活看工作树快照（L5）；群派活从最近 60 行人工摘，并记录"滚出窗口后丢了多少"。
3. 做两次扰动：用户中途改范围；让一次工具调用失败。
4. 验收只看四件事，不看模型自述：未完成项有没有被主动报出；迟到结果有没有标依据的版本；"还在工作"的提示与实际是否一致；最终产物逐条对照最初请求。
5. 对照组：同一任务，notice 里不写交付判据与收尾人。比较两组的人工介入次数与漏项数。

要检验的假设（判据取自[归档证据](../community/ds-bot/2026-10-29-requirements-evidence.md)）：

| 假设 | 可测判据 |
| --- | --- |
| H1 不区分"方案"与"执行"，管理员会把方案当交付 | 收到明确执行请求后是否出现实际派发/产物事件；错误完成声明数 |
| H2 任务归属只存在会话或提示词里，跨群与通知必然错位 | 同一任务在 Bot 视图、群视图、结果位置是否指向同一配置 |
| H3 角色只写在 instructions 里，人设不产生能力/权限/验收差异 | 两个人设 Bot 在同一任务上的工具、权限、验收差异 |
| H4 完成判定只看"最终回复"，回合结束会被当目标完成 | 部分完成/失败/取消被标为完成的比例 |
| H5 投递不等于采纳，目标修订后产物可能仍用旧版 | 修订后产物引用的目标版本、约束丢失率 |

样本与结论边界要一起记录：单任务、单模型、单宿主，不能推成普遍结论。
