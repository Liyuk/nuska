# 从用户目的到可验收结果：Agent 闭环的研究与工程现状

状态：一手资料案头研究 · 2026-11-01；未运行所列系统，未独立复现论文实验。

## 问题与方法

要判断的架构是：用户表达形成当前目标与约束，Agent 执行实际工作，根据证据验收，未达标时诊断并选择重试、改计划、补信息或请人判断；目标随新信息变化时，后续工作应遵循新的理解。本报告关注它是否已有先例、哪些反馈机制有效，以及什么证据能支持“更会解决问题”。

优先使用原始论文、作者/机构文档和公开实现；社区样本包括开源框架、原作者实践和一手 issue，不以帖子热度或 Star 数衡量效果。历史论文按指定版本阅读；官方网页以访问日为准。下面区分作者在给定实验中报告的结果、实现机制与本文的架构判断；2023—2024 年模型的结果不作为 2026 年所有模型的能力上限。

## 初步判断：闭环已有先例，可靠验收仍有条件

“规划—执行—反馈—修正”已经是明确的 Agent 研究路线。Magentic-One 直接实现任务账本、进展判断、循环检测和重新规划；Self-Refine、Reflexion、CRITIC 分别探索同模型自评、反思记忆和外部工具反馈。因此，把 Supervisor、持久状态和反思循环连接起来，本身不是新的架构原理。[Magentic-One v1](https://arxiv.org/html/2411.04468v1) · [Self-Refine v2](https://arxiv.org/abs/2303.17651v2) · [Reflexion v4](https://arxiv.org/abs/2303.11366v4) · [CRITIC v4](https://arxiv.org/abs/2305.11738v4)

但现有证据没有支持“增加一次自我批判就能普遍正确验收”。反馈来源、任务是否可验证、评价器是否可信以及额外推理预算，都会改变结果。需要把运行机制存在、特定基准提升和开放真实工作可靠性分别验证。[TACL 2024 自纠错批判性综述](https://aclanthology.org/2024.tacl-1.78/)

## 最接近的已有架构：Magentic-One

Microsoft Research 的 Magentic-One（论文 v1，2024-11-07）以 Orchestrator 指挥浏览器、文件、编码和终端等功能型 Agent。外层 Task Ledger 保存已知事实、待查事实、待推导事实、猜测和计划；内层 Progress Ledger 判断请求是否完成、是否循环、是否有进展，以及下一个执行者和指令。停滞超过预算后，系统更新账本并重新规划，直到完成判断或尝试/时间预算耗尽。它已覆盖本次设想中相当大一部分“保存理解—监测进展—反思改路”的结构。[论文 §4.1](https://arxiv.org/html/2411.04468v1#S4.SS1)

这仍有重要边界：账本是任务期间的工作记忆，完成和进展仍由 Orchestrator 判断；论文的最终正确性来自 GAIA、AssistantBench 和 WebArena 的外部评测。该结果没有证明 Orchestrator 自己就是可靠验收器。作者还明确指出，其评价重最终准确性，成本、延迟、用户偏好与用户价值尚未被充分覆盖。[论文 §5–6](https://arxiv.org/html/2411.04468v1#S5)

本文判断：单纯提出“一个领导 Agent 管多个角色并反思”差异有限。更有检验价值的区别是，能否追踪目标修订和证据的关系、发现错误完成声明、管理过期成果，以及用更少的人类干预和成本达到同等或更好的交付质量。

## 自我批判：不同反馈来源不能混为一谈

| 工作与版本 | 实际机制 | 可支持的结论与边界 |
| --- | --- | --- |
| [Self-Refine，2023，v2](https://arxiv.org/abs/2303.17651v2) | 同一个 LLM 生成初稿、产生反馈、迭代改写；不更新模型权重。 | 作者在七类任务中报告改进，证明这种流程值得实验；不能把这些任务上的偏好或分数变化推成通用长任务自主验收。 |
| [Reflexion，2023，v4](https://arxiv.org/abs/2303.11366v4) | 从任务反馈形成语言反思，存入 episodic memory，用于后续尝试；反馈可来自外部或内部模拟。 | 展示试错记忆能改善部分任务；语言记忆与权重学习不同，反馈质量和具体任务设置仍是条件。 |
| [CRITIC，2024，v4](https://arxiv.org/abs/2305.11738v4) | 使用检索、代码执行等工具检查已有输出，再根据反馈修改。 | 强调外部工具反馈的价值；工具返回的可核查事实比无依据的自信评分更适合支撑验收，但工具覆盖不到的目标仍需其他判断。 |
| [Large Language Models Cannot Self-Correct Reasoning Yet，ICLR 2024，v2](https://arxiv.org/abs/2310.01798v2) | 检查无外部反馈、只靠模型自身能力的 intrinsic self-correction。 | 在作者测试的推理任务与当时模型中，自纠错有时无益或降低表现；这不是“所有后续模型永远无法自纠错”的定理。 |
| [When Can LLMs Actually Correct Their Own Mistakes?，TACL 2024](https://aclanthology.org/2024.tacl-1.78/) | 批判性梳理自反馈、外部反馈和训练等不同设定。 | 综述认为可靠外部反馈和训练是重要条件，也指出不公平评价和特别适合自纠错的任务可能高估一般效果；该综述只覆盖其研究时期。 |

这些资料共同提示一个工程问题：执行者和 Reviewer 分成两个会话，不会自动产生独立证据。若它们共享相同错误信息或同样看不到真实结果，第二个模型仍可能同意错误结论。本文建议按每项验收条件选证据：程序检查、外部系统状态、来源核查、视觉检查、经过校准的模型判断或人工决定，而不是把所有条件交给一个泛化的“评分 Agent”。这是架构建议，尚需对照实验。

## 验收如何研究：已有基准能测什么

| 基准/方法 | 接近本问题的地方 | 不能直接推出什么 |
| --- | --- | --- |
| [τ-bench，2024，v1](https://arxiv.org/html/2406.12045v1) | Agent 在领域工具、政策规则和模拟用户的多轮互动中完成任务；用最终数据库状态对照标注目标，pass^k 检查重复尝试的一致性。 | 领域和目标状态预先定义，用户由模型模拟；它没有覆盖任意开放作品的质量、无限期目的变化或真实用户满意度。注意 pass^k 关注 k 次都成功，不是多试几次中至少成功一次。 |
| [τ²-bench，2025，v1](https://arxiv.org/abs/2506.07982v1) | 在 Telecom 双控制环境中，用户和 Agent 都能通过工具改变共享状态，专门研究沟通与协调。 | 更接近人机共同工作，但仍是可控领域与模拟环境；其结果不能替代生产交付实验。 |
| [OSWorld，2024，v1](https://arxiv.org/abs/2404.07972v1) | 真实电脑应用与跨应用任务，配初始环境和执行式评价脚本，以实际状态而非“我做完了”判断结果。 | 每项任务已有评价配置；尚不能说明 Agent 可以自己为新任务生成同等可信的验收器。原始论文分数不是当前模型排行榜。 |
| [METR Task-Completion Time Horizons](https://metr.org/time-horizons/) | 按人类专家完成任务所需时间刻画难度，并拟合不同成功概率下的任务时长；有助于区分能偶尔完成和可靠完成。 | 时间轴是人类任务耗时，不是 Agent 自主运行时长；任务主要是自包含、标准清楚的软件工作，不代表任意日常工作或多年项目。 |

METR 自己特别提醒：50% time horizon 不意味着低于该时长的任务都适合委派；现实价值还取决于人的提示、等待、检查和补救耗时。因而本项目不能只看 Agent 的最终通过率，也应计入验收成本与用户劳动。[METR：Time horizon 的限制，2026-01-22](https://metr.org/notes/2026-01-22-time-horizon-limitations/)

## 行业工程实践：已经出现与目标闭环直接接近的实现

| 实现与资料 | 已公开的机制 | 证据边界与可复用部分 |
| --- | --- | --- |
| Anthropic，[Building effective agents](https://www.anthropic.com/research/building-effective-agents)，2024-12 | Evaluator-optimizer 循环让生成结果接受评估和反馈，再迭代改进；适用前提是评价条件清楚、反馈确实能改善结果。 | 说明这种架构模式已进入厂商工程方法；不是通用自主验收的可靠性证明。 |
| Microsoft Agent Framework，[Magentic orchestration](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic) | 经理维护计划和进度，检测停滞并重新规划；支持人工计划审阅，发布计划、重规划和进度事件。 | 比固定群聊路由更接近自适应控制；官方也注明，超出原始 Magentic-One 设计的表现未得到验证。 |
| LangGraph，[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)；LangChain，[Deep Agents](https://www.langchain.com/deep-agents) | Checkpointer 保存单线程图状态，Store 保存跨线程数据；Deep Agents 提供规划、文件系统、子代理隔离与上下文压缩/卸载。 | 可复用运行和上下文基础设施；恢复执行状态并不自动定义目标正确性，也不保证恢复外部副作用的一致性。 |
| Letta，[Stateful agents](https://docs.letta.com/concepts/stateful-agents)；[v1 SDK memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks) | 当前文档将身份与多条 conversation 区分，并用 MemFS 保存跨对话记忆；v1 SDK 的 block 机制可让多个 Agent 附加同一份持久块，再注入各自上下文。 | “相同身份、多对话入口、持久记忆”已有实现。两代接口应分别理解；共享存储不会自动消除各次推理的上下文成本，也不等于目标与证据一致性协议。 |
| DSPy，[GEPA](https://dspy.ai/current/tutorials/gepa_ai_program/) | 根据轨迹、评价指标和文本反馈反思并生成新 prompt，搜索更好的程序配置。 | 这是跨样本优化 Agent 程序的方法；训练/验证集上的改进不等于一次开放任务中自动理解新目的。 |
| OpenAI，[Agent Improvement Loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)，2026-05-12 | 把真实轨迹、人类/模型反馈转成可重跑 eval，再提出 harness 修改供 Codex 实施。 | 展示跨运行改进工作流；属于开发迭代，不应当作每次任务内部的无人验收机制。 |

### 最接近本研究设想的工程案例

Anthropic 在 2026-03-24 的 [Harness design for long-running application development](https://www.anthropic.com/research/harness-design-long-running-apps) 中公开 planner、generator、evaluator：从简短要求生成 spec，生成者与评估者先协商阶段完成条件，评估者用 Playwright 操作实际应用，再将失败项交回修改。这已经涉及“表达→条件→执行→验收→纠偏”，也尝试按设计准则评价主观质量。文章同时承认评估者需要人工样例校准，会漏掉深层问题；模型升级后，部分阶段性监督反而成为额外成本。

这是一方工程案例，不是通用能力证明：文中一个案例的单 Agent 与完整 harness 分别运行约 20 分钟/6 小时、花费约 9/200 美元，计算预算明显不同，不能把成果差异完全归因于多 Agent 或 evaluator。Planner 被鼓励扩大功能范围，也提醒我们：更丰富的 spec 不自动等于更符合原始目的。此处的费用是文章当时案例，不能用于估算当前项目价格。

## 社区实践：持续循环已经普遍可构造，终止与验收仍是独立问题

Ralph 是有代表性的公开实践。[原作者说明](https://ghuntley.com/loop/)把它描述为单仓库、单进程、每轮推进一个任务的循环；[官方插件 README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/ralph-loop/README.md)则用 Stop hook 重复送入 prompt，以完成字符串或最大轮数终止。该文档明确把清晰条件、自动验证任务列为适用场景，而把需要人类判断或条件不清的任务列为不适用。源码行为表明“继续工作”的驱动已很容易搭建，完成字符串本身仍是执行者声明。

一手 issue 也揭示了控制机制的具体失效：用户报告 [v1.0.0 在正确完成字符串后仍持续重注入](https://github.com/anthropics/claude-plugins-official/issues/3632)，另一份带复现的报告指出 [缺失标签的文本也可能触发结束](https://github.com/anthropics/claude-code/issues/81827)。这些是特定版本、未在本报告复现的用户报告，不能推出所有循环方案的故障率；它们说明退出信号的可靠投递/解析和成果实际正确是两项分别要验证的工作。报告不根据 issue 关闭状态推断修复情况。

## 三种“自我改进”应分别评估

1. **同一任务内纠偏**：结果不合格，依据新证据补做、换路或重新理解目标。Magentic、generator/evaluator 和外部反馈研究属于这一类。
2. **跨任务积累经验**：把偏好和失败经验保存到记忆，供未来任务读取。它依赖记忆筛选、来源、更新和失效机制；记住错误也会扩大错误。
3. **开发阶段优化系统**：基于任务集、轨迹和反馈改变 prompt、工具或 harness。GEPA 和 trace-to-eval 工作流属于这一类；仍要在留出任务上检查泛化与回归。

三者可以组合，但不能拿某一类的成功代替另外两类的证据。


## 对当前架构设想的评判

从这组样本看，组件成熟度并不一致：

| 能力 | 已有证据支持的阶段 | 仍需验证的内容 |
| --- | --- | --- |
| 状态保存、跨会话上下文、工具运行 | 框架提供可使用的工程组件 | 实际部署的副作用重放、状态冲突、过期信息和成本。 |
| 目标分解、进度判断、停滞后重新规划 | 有公开算法、实现、基准与工程案例 | 任务领域迁移、评价器误判、目标被过度扩写或静默替换。 |
| 结果验收和主动纠错 | 在可验证任务或有校准标准的任务中有直接先例 | 评价条件覆盖是否足够、证据可靠性、错误放行和误拒绝。 |
| 开放目标持续变化下的可靠自主交付 | 本次材料没有给出覆盖任意场景的综合证明 | 新旧约束冲突、过期成果、隐含偏好、用户价值与总成本。 |

已有工作足以把它定位成一个已有研究谱系中的工程方向：根据目标组织行动，再借反馈选择继续、修正或结束。它值得做，但目前不能以“有 Supervisor”“会自我批判”“有多个角色”作为差异化证据。更可检验的研究问题是：系统对用户当前目的的理解能否随新证据修订，同时保留原有约束，并准确地验收结果。

一项实际产物可能通过技术检查却偏离用户目的；也可能内容正确，但太迟、太贵或无法使用。Magentic-One 已把后一类用户价值与主观开放任务评价列为限制。本文判断，真正需要补足的是验收的效度、目标变化后的影响追踪，以及在不确定条件下何时继续投入、何时请人判断的决策，而不只是增加循环次数。[Magentic-One §6.2](https://arxiv.org/html/2411.04468v1#S6.SS2)

工程上可复用已有运行框架，把研究重点放在目标修订如何影响已完成工作、每项条件对应什么证据，以及下一次检查/重做是否值得。Anthropic 的[多 Agent 研究系统报告](https://www.anthropic.com/engineering/multi-agent-research-system)明确讨论高 token 消耗，并指出需要全体共享上下文或有很多依赖的工作不一定适合并行多 Agent；这一结论是其系统经验，不是统一成本定律。本文建议按任务风险、结果不确定性和纠偏收益选择验收强度，避免每步固定调用完整监督团队。

验收自身也必须接受评价。[Anthropic 的 Agent eval 工程说明](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)区分轨迹与环境最终状态，并建议组合代码、模型和人工 grader，校准模型评分。对本项目，应同时测“错误结果被放行”和“正确结果被误拒”，并用独立留出任务验收系统表现。开发者在离线评测中持有标准答案，不意味着部署中的 Agent 能获得同等反馈；运行时自检与离线性能评估不能混用。

## 建议的验证边界

先固定一种任务和可核查产物，比较基础执行 Agent、增加反思但无新证据、增加外部验证反馈三种条件。记录目标达标率、错误完成声明、失败后修复率、总模型/工具成本、端到端延迟和人的介入劳动；相同预算与相同任务条件下再比较。

之后再加入目标中途修订、工具失败、中断恢复与冲突证据。给目标与验收条件编号，检查修订后哪些成果应重新验收；将“发出新指令”“执行者读取新指令”“结果遵循新目标”作为三个不同观察点。该协议是本文建议，未开展实验。

## 局限

这是一手资料抽样，不是系统性综述，也不表示所有社区方案都已覆盖。历史论文用于确认先例与反馈条件，没有将其数字当作当前产品表现；官方网页可能更新。没有运行任何项目，没有验证实现与论文版本的一致性，也没有证明版本化 Goal 对象本身能提高成功率。它只是一种让目标变化与证据关系可检查的设计手段，收益需用上述实验验证。
