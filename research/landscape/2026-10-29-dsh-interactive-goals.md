# 基于 DeepSeek Harness：构建目标驱动的多 Bot 群聊与交付

状态：研究与方案草案 · 2026-10-29

研究对象：DeepSeek Harness 源码快照 [`219cc443`](https://github.com/deepseek-ai/deepseek-harness/tree/219cc4434efe27bb38573d98e79b4ddc714dacea)。本文依据公开源码和文档，不报告运行实验，也不预设 Nuska 已选择 DSH 作为底座。DSH 处于开发预览阶段，接口可能变化。

## 1. 我们要做什么

人以明确目标提出愿望，Agent 随后理解并推进；工作期间，人可以依据新信息补充上下文、修改方向或停止。系统应提供可用的阶段性成果，并最终给出可检查的交付，而不是仅在某一轮宣称“完成”。

目标体验是 Grok Bot 式群聊：人给出明确目的，一个或多个 Bot 自主分工、领取任务、共享必要上下文，围绕最新目标推进，并交出阶段成果和最终产物。个体 Bot 有自己的记忆，群有共同的工作上下文；用户可以随时加入新信息或调整方向，而不需要持续主持每一步。DSH 为会话、Agent、工具、事件与目标续行提供可研究的底层能力；群聊、跨 Bot 任务和可靠验收仍是上层候选方案。

用户提到 DSH 底层可能有一套“AGI”实现。本次检查没有发现名为 AGI 的对应组件；下文围绕实际可定位的 `goal`、Agent 生命周期和扩展机制展开，不把目标续行称作通用人工智能。

## 2. DSH 已经提供了什么

### 同会话目标状态

[`dsh-goal`](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/packages/goal/goal/README.zh.md) 在现有 Agent 会话中保存一个当前目标。创建、编辑、暂停、恢复、完成、阻塞和清除等操作形成带 revision 的状态变更；`goal/change` 写入会话事件日志。状态恢复与事件回放共享同一持久来源，并用目标 id 和 revision 防止基于过期引用修改。

这不是独立任务数据库：同一会话最多一个当前目标，且该包负责目标状态，不负责选择何时继续或验证目标是否真的完成。

### 模型与人的控制入口

[`dsh-tool-goal`](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/packages/goal/tool-goal/README.zh.md) 暴露 `create_goal`、`get_goal`、`update_goal`。文档说明模型可从直接的人类请求推断长期目标意图；创建和编辑等动作受来源与当前运行状态限制。另有面向人的 [`/goal` 命令](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/packages/goal/command-goal/README.zh.md)。

这为“通过自然对话提出或修改目标”提供接口；它不证明模型每次都能识别真正目的，也不意味着所有文本都会自动成为目标修订。

### 后续轮次与用户输入

[`dsh-goal-round-driver`](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/packages/goal/goal-round-driver/README.zh.md) 在 Agent 空闲、目标 active、续行已启用且轮次有剩余时，安排同会话的下一次 Goal Round。它在准入前后核对目标版本；普通人类消息不消耗 Goal Round 上限，有竞争的人类工作会优先于自动轮次。更一般的实时输入与状态机制见 [Agent 生命周期](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/docs/agent-lifecycle.zh.md)。

此外，2026-10-29 查看上游较新快照 [`f3803c96` 的驱动器文档](https://github.com/deepseek-ai/deepseek-harness/blob/f3803c96974ad4a94195fb97e5c637e9c2a3afe3/packages/goal/goal-round-driver/README.md)时，文档指出加载 subagent 服务时会等待正在推进的后代 settle；具体运行时行为与旧版本的差异尚需测试。

因此它并不只是无限调用模型：持久状态、版本检查、用户输入和轮次准入都有明确语义。与此同时，驱动器的停止条件及恢复边界应被视为设计约束，而非可忽略的实现细节。

### 恢复与授权

目标 phase、revision 和历史可随会话恢复；但续行启用状态只在进程内有效。恢复、fork 或驱动器重建后，active 目标不会自动开始工作，需要显式 resume 重新授权。暂时性的提供方或持久化失败也不会由该驱动器隐式重试。轮次上限与时间等运行边界是不同机制。[目标状态](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/packages/goal/goal/README.zh.md) · [续行驱动器](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/packages/goal/goal-round-driver/README.zh.md)

## 3. 它没有直接解决什么

- **目的是否理解正确**：能创建 objective，不等于能够从模糊愿望可靠推断目的、边界和验收要求。
- **完成是否真实**：文档明确没有独立评估器；完成与阻塞仍由策略和调用方判断。提示词要求提供证据，不等于存在自动验收机制。
- **会话之外的目标连续性**：设计是同一会话目标，不是跨会话、多 Bot 的任务系统。会话分段、委派和任务所有权需单独设计。
- **失败处理**：轮次上限不代表外部副作用成功；是否安全重试，需要实际状态和具体工具配合判断。
- **交付感**：有目标、进度或多轮执行，不自动等于符合用户目的的完整产物。

## 4. 从底层能力到团队交付：候选架构

下面是 Nuska 的**方案假设**，不是 DSH 已有功能，也不是对 Grok Bot 服务端实现的复刻。Grok Bot 逆向资料中可见成员回合与部分协议，但服务端派发、领取、记忆合并和完成判定等细节仍不透明；见[任务机制研究](2026-10-29-grok-task-mechanisms.md)。

```text
用户的目标 / 补充 / 纠偏
             ↓
群聊入口：人、Bot、群消息与阶段成果
             ↓
团队任务层：目标版本 → 工作拆分 → 派发 → 领取 → 结果与验收
             ↕
上下文与记忆：群工作上下文 / Bot 私有记忆 / 经授权共享的知识
             ↓
DSH 接入层：会话、Agent、工具、事件、可选 goal 与续行
             ↓
文件与工具结果 / 阶段产物 / 最终交付
```

[DSH 架构](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/docs/architecture.md)区分可持久重放的 `session/event` 与运行中的 `agent/*` 事件；插件通过 Cordis 组合。这个边界是候选接入点。补充核查：DSH 已有实验性 Agent Team，提供 Lead、成员、共享任务板、claim、依赖和消息；它的范围及不足见[DSH 现有能力组合研究](2026-10-29-dsh-multi-bot-composition.md)，不能再把团队任务原语视为完全不存在。Nuska 可以作为插件、组合插件集或外部服务，先通过实验决定；底层 DSH 不是已定选型。

### 4.1 群聊是任务入口，也承载可用的阶段结果

群聊里有人类、协调 Bot 和按需参与的成员。用户说出目标后，协调者识别预期交付、自行开始工作；能单独完成时不必强制组队，适合并行的方向则可交给不同成员。Bot 的消息保留来源、任务关联和目标版本，避免读者把讨论发言当作已交付结果。

用户在过程中提供新信息时，系统应在安全的执行边界尽快处理，并判别是补充、修改、追问还是停止。原有阶段成果保留其依据和版本，已过时的工作不得直接作为新目标的完成证据。消息已入队、被 Agent 领取、模型实际处理，是不同事实；不能只凭 `steer()` 返回或 Agent 空闲状态推断修正已生效。[DSH 生命周期与输入](https://github.com/deepseek-ai/deepseek-harness/blob/219cc4434efe27bb38573d98e79b4ddc714dacea/docs/agent-lifecycle.md) · [本人对中途消息的讨论 #651](https://github.com/Fei2411/DS-Bot/discussions/651)

**期望体验**：阶段性给出可以阅读或使用的成果，说明接下来会继续什么；无需每一步都让人确认。确实需要额外授权、关键信息不可获得或存在不可消解的歧义时，再明确请求人的判断。

### 4.2 任务分发、领取与汇总应可追溯

候选工作记录可包含目标版本、负责人、工作项与预期产物、交付或检查要求、派发和领取状态、结果、阻塞及证据。协调者应能查到**谁负责什么、是否实际收到、是否有结果**；“我已经安排”不等于调用已成功。

一个可研究的状态模型：

```text
待派发 → 已派发 → 已领取 → 进行中 → 已交付 → 待验收 → 已验收
                       ↘ 阻塞 / 失败 / 已取消 / 结果未知
```

派发与领取需要稳定关联标识；重复投递、迟到结果、超时及恢复须有明确语义。系统应区分“成员声称完成”和“检查确认完成”。是否需要独立任务对象、任务队列或基于宿主事件的投影，是待实验的设计选择；不要预设多一张表就能解决可靠性。让协调者对照最新目标检查和整合成员结果，不只把多个回答拼接。

已有讨论提出群外派发未送达、提醒未建立等体验问题；其根因需要复现，不能由用户反馈直接确定。[#643 跨群协作](https://github.com/Fei2411/DS-Bot/discussions/643) · [#652 自主交付与恢复](https://github.com/Fei2411/DS-Bot/discussions/652) · [#657 团队协作与评测](https://github.com/Fei2411/DS-Bot/discussions/657)

### 4.3 上下文和记忆：分层、可追溯、按需共享

| 层次 | 保存什么 | 给谁使用 |
| --- | --- | --- |
| 当前任务上下文 | 原始目标及修订、当前约束、阶段产物、未完成工作和证据 | 相关群和被授权的执行者，按当前任务需要读取 |
| 群共享上下文 | 群的共同决定、分歧、任务关系与可共享资料 | 当前群的成员；区分事实、模型建议和用户决定 |
| Bot 个体记忆 | 身份、个人工作经验、长期偏好及被允许保存的知识 | 对应 Bot；不得因为加入群而默认广播 |
| 经授权的共享知识 | 用户指定可复用的文档、结论和证据 | 有权限的 Bot、群或后续任务；标记来源与适用范围 |

**工作上下文不等于长期记忆。** 每个成员不必接收所有群历史；应获得任务所需的最新目标、相关约束、阶段成果及来源，并能回查原始记录。模型摘要是候选表示，不能自动覆盖用户原话或把推断升级为事实。记忆写入、检索、更新、冲突处理、权限、删除与溯源都需定义；实际项目中的个人和组织知识须由其拥有者决定共享范围。[DSBot 既有上下文设计](https://github.com/Fei2411/DS-Bot/blob/4a7b55069ad300eae8be42a74f31bc170b40ead7/docs/plans/2026-10-09-context-and-memory.md)

跨会话或压缩后，任务层需能恢复当前目标、责任归属、待办和证据，并让群成员按需重新取得上下文。`dsh-goal` 的权威范围是单会话；不能把它直接视作群的共享记忆或跨 Bot 任务状态。Graph Memory、DSH Mnemon 和 DSBot 是可研究的外部实现，尚需实验判断其机制是否提高任务完成质量。

### 4.4 长任务不是单纯增加轮数

DSH 的 goal driver 可用于**单会话**续行，但它不会自行创建群任务或多 Bot 派发，重启后续行也需要重新授权。对于团队任务，先明确由谁拥有调度权及持久状态，避免 DSH 和上层调度器同时恢复同一工作。遇到等待外部事件时应研究事件驱动唤醒及停滞检测，而不是无限空转。

原 DSBot 被检查版本在 Bot 会话中屏蔽 DSH goal，并在群 Bot 间接力达到上限时停放后续接力；已经在执行的工具工作不一定被中断。[静态对比](2026-10-29-two-ds-bot-delivery.md) · [本人对接力结束条件的评论 #611](https://github.com/Fei2411/DS-Bot/issues/611#issuecomment-6463951739)。用户对这种设计的体验是它妨碍了交付；实际影响需要用特定版本和任务复现。候选方案是基于任务进展、阻塞、授权和验收判断是否继续，同时保留可停止、停滞检测与明确恢复机制，而不是简单删除所有限制。

### 4.5 阶段交付与最终验收

阶段交付需要有可使用的产物、对应目标版本、关键证据与后续工作；最终交付需要汇总最新目标下的产物、实际检查、未完成项和不确定性。自动检查负责适合机器判断的条件，人工评价或明确标注的评估用于内容质量和目的符合度。不能只看聊天总结、模型自评、任务状态或文件存在。

当前 DSH goal 文档明确没有独立验收器。能否在完成动作前接入可靠、不可绕过的验收层，需要进一步研究公开扩展点、权限、竞态和宿主是否允许；这里不声称已经实现。用户反馈的“分析了却没有完成”“说已经派活但没有实际派发”等，应当转化为可复现测试，而不是依靠更长的提示词自行消失。

## 5. 用真实反馈驱动设计

| 既有反馈 / 体验 | 对 Nuska 的候选要求 | 验证方式 |
| --- | --- | --- |
| 停在分析、计划或发现问题，未继续交付（[#652](https://github.com/Fei2411/DS-Bot/discussions/652)） | 根据请求范围自主执行、修复和验收，提供实际产物 | 同任务比较实际产物、检查结果和未完成项 |
| 接力到达上限时任务尚未完成（[#611](https://github.com/Fei2411/DS-Bot/issues/611)） | 结束依据应能表达目标、实际进展和阻塞；仍保留可控停止 | 达到阈值前后检查派发、未完成任务及恢复 |
| 群外成员未收到任务，提醒未建立（[#643](https://github.com/Fei2411/DS-Bot/discussions/643)） | 派发及领取可追溯，结果不能凭承诺认定成功 | 核对派发记录、接收方实际事件和预期后续动作 |
| 运行中补充和纠正（[#651](https://github.com/Fei2411/DS-Bot/discussions/651)） | 记录何时接收、领取、实际处理，更新目标和后续工作 | 运行中修正目标，比较事件顺序与最终产物 |
| 群里结论和后续行动散落（[#676](https://github.com/Fei2411/DS-Bot/discussions/676)） | 阶段交付汇总成果、分歧、证据和剩余事项 | 对照源材料检查遗漏；总结不是完成证明 |
| 长上下文换段可能遗漏约束（[#564 评论](https://github.com/Fei2411/DS-Bot/issues/564#issuecomment-6463576325)） | 保持目标、修订、责任与证据可追溯 | 强制换段后核对约束与工作连续性 |

这些是用户提出的问题或体验，不代表每一项在当前版本仍可复现。更详细的社区背景见 [#657](https://github.com/Fei2411/DS-Bot/discussions/657)。

## 6. 最小实现与对照实验

先做一项群研究任务：用户提出明确问题，协调 Bot 可按需委派两个相互独立的资料方向，最终交一份有来源的报告。用户中途补充一条改变范围的信息；至少一次工具请求模拟失败。要求系统先交出可阅读的阶段发现，再交最终报告。

1. **记录基线**：固定模型、权限和宿主版本，记录现有 DSH/DSBot 的实际事件、用户消息与产物；不把用户推测当作已观测故障。
2. **最小原型**：在宿主可支持的接口上关联目标版本、一个派发/领取记录和交付证据；不预先构建完整平台。
3. **测试共享上下文**：成员只获得被授权且与任务相关的信息；修正后可查到新的目标版本，旧结果保留来源和版本。
4. **测试故障与恢复**：检查派发未送达、成员迟到、工具失败、接力暂停和重启后的状态；外部效果未知时核实再重试。
5. **独立验收**：检查来源可访问、结构与关键要求；由人评价研究质量、目的符合度及阶段成果是否可用。记录未完成项、虚报完成与不必要的催促。
6. **跨宿主比较**：首个方案跑通并记录限制后，再对照第二个宿主，决定哪些能力可复用。

## 7. 待解决的关键问题

- 群任务事实来源、DSH 会话日志和 Bot 独立上下文如何关联；目标变更与迟到结果如何处理？
- 哪些接口真正允许注册群消息、启动/恢复 Agent、观测事件和注入上下文？对不同 DSH 版本如何验证？
- DSH goal 与任务分发层如何协调，特别是续行授权、重启及重复副作用？现有 DSBot 的限制是否允许插件方式接入？
- 个人记忆与群共享知识如何控制权限、来源、冲突与更新？
- 什么阶段成果可用；验收能否覆盖用户目的，而不只是检查格式或模型报告？

这些问题需要原型和证据回答。本文章不宣称 Nuska 已实现这些能力，也不把 Grok Bot 的未知内部机制视为事实。
