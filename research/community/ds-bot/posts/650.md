# 建议：自托管的远程 Bot 工作区，让团队持续工作并随时访问

## 想解决的问题

DS Bot 的团队和记忆会长期存在，但用户不一定一直坐在运行它的电脑前。希望 Bot 团队在用户自己的常开设备或 VPS 上持续工作，用户可以从手机、笔记本或另一台电脑随时交代任务、查看进度和取回结果。关闭访问页面后，任务仍能继续。

例如：家里有 NAS 或小主机，早上在手机上安排整理资料的任务，晚上再查看结果；或者用户已有 VPS，希望把 Bot 团队部署在那里，从不同设备连接同一个团队。

相关讨论：[一个基于 Docker 的云端 DeepSeek-Bot 部署方案 #272](https://github.com/Fei2411/DS-Bot/discussions/272)，其中分享了社区部署项目。这里想进一步讨论用户需要什么样的远程工作体验，而不限定某个部署项目。

## 面向谁

- 已有 NAS、家庭服务器、常开电脑或 VPS，愿意自己运行和维护服务的人。
- 希望从多台设备访问同一个 Bot 团队，同时自己选择数据存放位置的人。
- 希望设备离线时能清楚知道发生了什么，而不是误以为 Bot 仍在工作的人。

普通桌面用户可能也需要手机访问，但未必有常开设备或愿意配置服务器；这个方案是否能覆盖他们，需要另外讨论。

## 产品方向（提议）

把**运行 Bot 的设备**和**访问 Bot 的设备**区分开：用户在自己的 VPS 或常开设备上部署一个工作区，然后从浏览器或未来的客户端连接它。用户可以选择已有设备，而不是要求购买特定服务。部署方式和连接方式可以分开选择：

- **运行环境**：已有 Docker 环境、NAS、小主机或 VPS。先利用现有 Docker 部署；其他安装方式是否需要支持，听取用户反馈。
- **连接方式**：已有私有网络（如 Tailscale）里的地址，或通过带身份验证和 HTTPS 的反向代理／隧道访问。是否需要产品内的设备添加、连接检查或引导配置，以及是否支持多个工作区，尚待讨论；不预设 DS Bot 要自建隧道服务。
- **访问入口**：先考虑浏览器访问；桌面和手机是否需要原生连接入口，取决于用户场景和现有能力。

希望的用户流程是：选择或准备运行设备 → 部署工作区 → 建立安全连接 → 从自己的设备打开并登录 → 派任务、查看进度和结果。首次设置应明确数据保存在哪里、Bot 能访问哪些文件，以及设备离线后会发生什么。

## 需求与边界

第一阶段建议验证：

- 远程访问同一个团队，查看对话、运行状态和结果；关闭页面不应主动停止服务端任务。
- 能安全登录；网络连接断开、服务不可达和任务失败应有可理解的提示。断线重连后能查看已有状态，具体任务恢复能力需验证。
- 清楚配置工作目录和数据持久化，提供文件取回、备份、恢复及更新指引。
- 明确 VPS 与家中设备的责任边界：用户负责设备在线、网络、费用和维护；不要暗示数据永远只在本机。

可作为后续讨论：移动端通知、远程审批、多个工作区、浏览器操作和可视化执行过程。它们不应被当作远程访问第一版已具备的能力。

## 当前基础和限制

仓库已有 Docker 镜像、持久化数据目录和 DSH Web。当前 Docker 部署以容器为沙盒，只有完全权限；所有 Bot 能访问容器内可见的内容和挂载目录。Docker 版目前没有桌面应用的 Bot 浏览器，因此远程 Web 工作区还不等于完整的远程图形电脑。当前也没有在这里承诺现成的设备配对或隧道功能。

远程访问需要考虑身份验证、HTTPS、可信 Host 和 WebSocket。私有网络与公网隧道的暴露范围不同；宿主机休眠、停机或断网时，Bot 和访问都会停止。安全配置和恢复行为需要实际验证。

## 想听听大家的意见

1. 你想连接的是家里的 NAS／电脑，还是 VPS？平时会从哪些设备访问？
2. 你愿意自己用 Docker 和私有网络部署吗？首次设置最希望产品帮你完成什么？
3. 第一版最需要的是远程聊天和文件结果，还是浏览器操作、执行画面、通知和远程审批？
4. 对文件、登录状态和不同 Bot 之间的隔离，你有什么预期？
5. 你需要同时连接多个团队或设备吗？能在私有网络访问是否足够？

这是探索用户需求的提议，部署与连接方式、产品范围都还没有定案。
