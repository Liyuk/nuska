# 建议：Bot 有结果或需要关注时发送通知

## 背景

让 Bot 执行需要时间的工作后，用户常常切去做别的事；完成时如果没有提醒，就需要反复回来看。建议为 Bot 的结果和需要用户处理的情况提供通知，点击后直接回到对应对话。

## 参考：Grok Bot

[Grok Bot 官方说明](https://docs.x.ai/grok-bot/settings-and-notifications)提供每个 Bot 的通知开关，覆盖完成和等待用户处理；侧栏区分未读结果与需要关注。桌面和手机有不同的通知路由，正在查看的 Bot 可保持安静。它的[移动端说明](https://cursor.com/help/grok-bot/mobile)也说明每个 Bot 可以关闭通知。

这些资料没有证实它使用 Web Push，也没有定义“任务完成”的底层判定；下面是 DS Bot 的产品建议，不是对 Grok Bot 实现的描述。

## 建议的体验

- 在 Bot 详情中提供「通知」开关，覆盖完成和需要用户处理；明确显示本设备的通知权限状态，并由用户主动点击开启时才请求权限。保留侧栏未读和需要关注状态，通知权限关闭也不影响查看结果。
- 用户发起的工作产生可供查看的最终回复时，通知“Bot 有新结果”，避免把一次回复结束误称为整个目标已完成。需要批准或用户输入时，通知“Bot 需要你的关注”，不要把等待、失败或取消称作完成。Bot 之间的内部消息和流式中间内容不逐条通知；群聊按对话合并提醒，避免多人连续发言刷屏。
- 当前页面可见且用户正在查看该对话时不弹通知；切到其他对话或窗口在后台时可以提醒。点击通知聚焦应用并打开对应 Bot 或群聊。短时间内同一对话的多个结果合并，多个窗口不应对同一事件重复弹窗。
- 默认通知文案只显示 Bot 或群聊名称和事件类型，不显示任务内容或消息正文；通知只是提示，真实内容在打开对话后查看。

## 投递范围与分期

1. **先做正在运行的网页和桌面应用通知**：沿用已有的批准通知能力，统一为结果和关注提醒；网页或应用必须仍在运行。先验证通知的触发、权限、去重和点击跳转。
2. **再评估真正的 Web Push**：用户关闭网页后仍可收到通知，需要持续运行的 Bot 服务、受支持的安全来源、浏览器订阅和服务端推送投递；电脑休眠、服务停止或网络不可用时不能保证即时送达。要明确设备订阅的管理、撤销、过期清理和隐私保护。此阶段不承诺手机原生推送或跨设备智能路由。

现状：[approval-notices.js](https://github.com/Fei2411/DS-Bot/blob/dev/ds-bot/src/client/approval-notices.js) 只在页面运行且权限已授予时，为等待批准发出通知；不会主动请求权限。

## 验收场景

- 在 Bot A 等结果时切到 Bot B：A 产生最终回复后收到一条提醒，点击回到 A；继续查看 A 时不弹。
- 等待批准、失败和取消不会显示为完成；批准提醒可跳到相关对话。多个窗口和群聊连续消息不会造成重复刷屏。
- 权限未授权或用户关闭通知时不弹，侧栏状态仍可用；授权被拒绝时能看到如何到系统或浏览器设置中修改。
- Web Push 阶段单独验证关闭页面后的送达、点击、订阅撤销和失效清理；服务停止或设备离线时不承诺实时送达。

## 待讨论

通知开关默认关闭还是开启？群聊是按群配置还是跟随 Bot 设置？“最终回复”能否通过 DSH 支持的事件可靠识别，以及失败、取消和多窗口去重需要哪些平台能力？真正的 Web Push 是否值得在自托管场景引入推送服务？这些选择留待实现前确认，不依赖修改 DSH。
