# [Feature] 统一封装常用服务连接器：从邮件开始

## 想解决什么问题

DS Bot 已有 GitHub 连接器，也能通过 Settings → Capabilities 添加自定义 MCP 服务。但使用常见服务时，用户仍需要理解 MCP 地址、请求头、密钥和 Bot 分配等配置。建议把邮件、文档、日历等高频服务封装成易连接的入口，同时保留自定义 MCP，覆盖更多服务。

**建议先做邮件**：让 Bot 帮用户查找和总结邮件、整理待回复事项，并在用户检查后协助回复。以下是讨论提案，不是已确定的设计或排期。

## 现状与反馈

- **GitHub 连接器**使用 DSH 的 MCP 客户端，当前设计让所有 Bot 和会话使用其工具。
- **Capabilities** 已支持自定义 MCP：本地 stdio 或 Streamable HTTP，能力库由团队共享，能力按 Bot 分配；密钥通过密钥库引用。Bot 添加的本地命令需要用户批准。
- [#125](https://github.com/Fei2411/DS-Bot/issues/125) 有 Exa MCP 的实际使用反馈：URL 中的密钥引用未替换导致鉴权失败；报告者称改用请求头后调用成功，URL 问题后来由 [#167](https://github.com/Fei2411/DS-Bot/pull/167) 修复。
- [讨论 #203](https://github.com/Fei2411/DS-Bot/discussions/203) 有人询问 Bot 如何接入 MCP；[#631](https://github.com/Fei2411/DS-Bot/issues/631) 报告了共享能力可能变成孤儿及缺少使用者信息的问题，尚需核实。

这些反馈说明有人尝试和提出需求，不能据此推断使用规模。

## 建议方案：统一封装常用服务

对用户提供 Gmail、Outlook 等清晰的服务入口，展示连接账号、权限、状态、错误和断开方式；让用户选择哪些 Bot 可以使用。自定义 MCP 继续作为高级入口，支持接入未预置的服务。

底层优先复用现有能力库、密钥机制和 DSH 的 MCP 客户端，而不是为每种服务另造一套运行机制。服务方有兼容的 MCP 服务时优先直接接入；没有合适接口时再评估适配层。具体的账户、授权、挂载和生命周期如何统一，需要先验证 DSH 的公开 API；GitHub 当前是团队可用，不能假定已有按 Bot 隔离，迁移也需要兼容既有用户。

**邮件首版建议**：

1. 先根据需求和认证可行性选择 Gmail 或 Outlook 中的一家。
2. 首先支持搜索、读取和总结，并尽可能提供原邮件链接。
3. 回复先在聊天里生成文本；若支持在邮箱中创建草稿，作为单独的写权限启用。
4. 发送、转发、删除和批量操作后续再做，分别讨论授权和执行前确认。不能只靠提示词实施只读限制。

需要先验证服务方接口和 DSH 是否支持所需 OAuth 登录、令牌刷新、权限限制和撤销；不能支持时向 DSH 提需求，不修改 DSH。断开时清理本地凭据；是否能撤销服务端授权按服务说明。

## 建议顺序和优先级

| 顺序 | 优先级 | 范围 |
| --- | --- | --- |
| 1 | P1 | 选定一家邮件服务，验证 MCP、认证及只读操作；随首个连接器完善必要的连接状态和权限体验。 |
| 2 | P1 | 邮件搜索、读取和总结；评估单独授权创建草稿。 |
| 3 | P2 | 在权限和确认机制可靠后，讨论发送、转发、删除等邮件写操作。 |
| 4 | P2 | 按需求扩展日历、网盘 / 文档、Notion 或 Microsoft 365，复用已验证的流程。 |
| 5 | P2 | 改善已有自定义 MCP 的配置指引、错误提示和使用者可见性；探索经过验证的服务模板。 |
| 6 | 待评估 | 等 DSH 官方支持 MCP Apps SEP-1865 后，再评估连接器交互界面，遵循现有设计，不自建宿主。 |

优先级仅供讨论，可根据用户需求和接口可行性调整。Grok 的[连接器文档](https://docs.x.ai/grok/connectors)可作服务类别参考，但它自带的集成不能直接视为 DS Bot 可用。

## 希望听听大家的经验

3. 连接账户时，是否应该由用户选择可用的 Bot？哪些操作需要每次确认？
4. DSH 的公开 API 在 OAuth、Bot 级权限和写操作确认方面有什么已知能力或缺口？
