## 问题与范围

要回答三个问题：公开讨论里，作者对「意图 → 派发 → 执行 → 验收」这条链路提出了哪些要求；哪些环节被报告为失败或存在结构边界；这批材料能把结论支持到什么程度。

对象与版本：`Fei2411/DS-Bot` 的 22 篇 Discussion 原帖，编号 #638–#678，创建时间集中在 2026-10-28，快照日期 2026-10-29（`README.md:3`）。其中多数是产品建议或讨论，另有一篇贡献询问（`653.md:10`）和一篇工程稳定性提案（`678.md`）。同批材料另有五份研究笔记：主题索引、评测方案、执行参考、记忆与上下文、意图到交付。

不包含：维护者和其他参与者的回复（`README.md:3`「其他人的帖子和回复不在此转载」）；DS Bot 的实际运行复现；Grok Bot 的官方实现细节；任何对照实验结果。帖子后续的编辑与当前状态以 GitHub 原讨论为准。

脱敏规则：原帖归档仅保存作者公开发布的原文及出处；本报告对需求作概括，不复述个人环境、具体 Bot 名称或群名称。涉及个人环境的内容概括为「公开讨论中报告的一次情况」。引用行号未作调整，含个人环境措辞的句子改为转述而不直接引用。

同一类问题在状态显示上反复出现（B4）：提醒列表为空时无法判断是没创建、没执行还是没显示（`643.md:12`）；摘要「生成中」与卡住不可区分，无可用 Bot 的群也可能仍显示生成中（`677.md:12`、`677.md:14`）；`scanning` 结束被当成所有 Session 读取成功（`644.md:25`）；「最多等待 6 秒」被误当成总响应上限（`644.md:23`）；设备离线时用户可能以为 Bot 仍在工作（`650.md:22`）；一次回复结束曾被当成目标完成（`656.md:23`）。

**「回复了处理方案，但没有推动成员执行」是本批材料的集中点**，但要注意它描述的是群管理员 Bot，不是维护者：

- 收到明确执行请求后只回方案，等用户再次确认（`676.md:29`）。
- 分发后停在方案、计划或「是否继续」（`676.md:31`）。
- 只汇总「建议先调研、再写报告」就停下，被作者点名不可接受（`676.md:33`）。
- 判据：方案与自报完成都不算交付证据（`676.md:35`）。
- 机制层：任务驱动不能只依赖模型说「已经安排」（`synthesis:15`）；「我来处理」只是声明，必须另有派发、接收、执行和产物证据（`execution:15`）。
- 通知层：一次回复结束不能被当成整个目标完成（`656.md:23`）。

归档中没有维护者回复（`README.md:3`），因此这组证据不能读成「维护者用方案敷衍作者」。同样，`653.md:10` 直接询问 collaborator 路径，归档里没有回应记录，只能记为「未见回复」，不能记为「被拒绝」。

### 交付判据

最具体的一条是四态收尾：`657.md:60`「最终区分完成、部分完成、等待用户和结果未知」，并给出「产物位置、验证依据、剩余问题与下一步」。这条同时规定了状态枚举和交付内容。

第二条是逐条必要条件：`evaluation:57`「最终完成必须满足全部必要条件」，并要求「必要条件逐条标记通过、失败或无法判定」「展示分项而不只给平均分」。配套指标是「产物满足全部必要条件的运行数 / 有效运行数」（`evaluation:13`），分子与分母都要列出。

第三条是证据门槛：`676.md:35`「不把方案或自报完成当成交付证据」；同帖更早就点名「不能只汇总“建议先调研、再写报告”的方案后停下」（`676.md:33`）。次一级的强判据还有「以独立的任务检查和必要的人类判断为准，不只看 Bot 是否声称完成」（`657.md:83`），以及把状态、模型报告和检查结果分开（`execution:21`）。

| 角色 | 职责 | 出处 |
| --- | --- | --- |
| 任务负责人 Bot | 汇总关键结果，但不吞掉分歧 | `657.md:56` |
| 发起派活的 Bot | 对照原目标综合验收，不能只转发一段报告 | `652.md:25` |
| 群管理员 | 对用户目标负责到可用产物；不得把成员自报完成当证据 | `676.md:31`、`676.md:35` |
| 独立检查 | 对机器可检验的条件运行独立检查 | `execution:21`、`evaluation:21` |
| 人工与用户 | 目的符合与质量由人评，必要时双人复核，最终对齐最新授权目标 | `evaluation:7`、`evaluation:15` |
| 模型自评 | 明确不能作为唯一裁判 | `evaluation:21` |

证据类型同样是分开的：产物本身（`evaluation:14`「不以文字声明代替产物」）；产物位置加验证依据（`657.md:60`）；声明、外部状态与检查结果三者对照（`evaluation:17`）；阶段成果单独评价而不把中间消息数量算成进度（`evaluation:16`、`evaluation:57`）；修订前的阶段成果不被新目标抹掉（`evaluation:55`）；恢复前先查真实产物与外部状态，不确定副作用是否发生时不要盲目重复操作（`657.md:62`）；完整运行记录（`evaluation:34`）。投递与采纳也必须分开：`context:42`「向某个成员投递上下文不证明它已采纳」。

### 角色与分层

材料里出现了「哪些角色差异需要真正的工具、权限或验收约束」（`657.md:94`）这样的追问，也就是角色名不等于能力或权限。这是接近 Nuska 核心论点的部分：

| 判断 | 出处 |
| --- | --- |
| 全能模型下，只有「研究员」「工程师」这样的人设容易失去区分度 | `657.md:49` |
| 角色差异需要真正的工具、权限或验收约束 | `657.md:94` |
| 场景模板应包含工作方式，而不只是角色名称 | `645.md:30` |
| 提示词不能替代权限：只读限制不能只靠提示词实施 | `639.md:36` |
| 改变他人行为需权限边界，不是「设定」就能做到 | `643.md:24` |
| 侧栏分组不改变身份、成员、会话、权限或工作目录 | `638.md:29` |

「谁对最终交付负责」也被明确要求，且要求每次任务指定：`657.md:52`「一次任务里明确谁对最终交付负责」，同段区分「提供某项专业支持」与「在需要时独立审查」；`657.md:53`「专业可以重叠，但下一步和交付的责任应清楚」。责任被分别放到群管理员（`676.md:31`）和发起 Bot（`652.md:25`）身上。但材料没有给出承载该责任的持久字段：`657.md:45` 说「不一定要做成任务看板或结构化任务对象」，`675.md:29` 才在定时任务语境提出结构化关系。

| 层 | 内容 | 出处 |
| --- | --- | --- |
| 长期身份 | 关注点、熟悉的上下文、能力、权限、交付习惯 | `657.md:51` |
| 本次任务职责 | 谁对最终交付负责、谁提供某项专业支持、谁独立审查 | `657.md:52` |
| 团队层 | 群内路由、负责人、交接、共享任务状态与可见进度 | `657.md:69` |
| Harness 层 | 工具执行、权限、事件、取消、恢复，限 DSH 公开能力 | `657.md:70` |
| 界面层 | 让用户检查和纠正目标、证据、阻塞与交付 | `657.md:71` |
| 运行环境责任 | 插件、DSH、桌面应用各自能观测什么，哪些故障不可见 | `678.md:30` |

材料里的角色观可以概括为「责任可以指定，权限不能靠指定」：`676.md:31` 要管理员对目标负责，`643.md:24` 又不允许它随意改其他 Bot；`657.md:94` 要求角色差异落到工具、权限与验收；`639.md:36` 明说提示词不能实施只读。四句连起来就是「persona 不是权限系统」，虽然原文没有用这个措辞。作者也没有设置永久反对派的角色，而是要求用证据、反例和验收标准形成分歧（`657.md:54`）。

## 局限和未解问题

- **归档范围**：只收作者本人原帖（`README.md:3`）。所有涉及分歧的说法都只能引用作者自己的预判与自我限定，不能证明维护者提出过什么反对意见，也不能证明哪些建议被接受。
- **范围与引用不一致**：`themes:3` 写的是「公开讨论及一条公开 issue 评论」，正文却引用两条 issue 评论（`themes:13-14`），且都不在归档内。
- **没有实测**：主题笔记自述「不是社区共识、产品评测或已验证的性能结论」（`themes:3`），评测方案自述「没有已运行的结果或排名」（`evaluation:3`），执行参考自述是资料调研（`execution:3`），意图到交付自述不报告对照实验结果（`synthesis:3`）。
- **关键失败未复现**：跨群提醒为空「原因尚未复现」（`643.md:12`）；记忆面板问题「尚未复现具体用户环境中的卡顿」（`677.md:14`）。
- **没有量化**：用量页「尚未采集具体耗时或性能分析数据」（`644.md:12`）。
- **二手资料未经证实**：第三方 Grok Bot 提示词「来源、完整性及是否为当前线上版本均未经验证」（`652.md:16`）；plan/goal 模式「尚无证据证明它内部实际存在这两个模式」（`652.md:29`）；Grok 分区细节与拖拽操作也未实际验证（`638.md:20`、`649.md:20`）。
- **作者自标的误读风险**：使用体验未经同任务跨模型评测（`652.md:12`）；引用功能「尚未完成真实界面验证」（`648.md:31`）；稳定性缺口「不表示已经发生过相应故障」（`678.md:14`）；「未证明提议方案能够提高质量」（`themes:20`）。
- **时间性**：快照固定在 2026-10-29，帖子可能已被编辑，回复状态以 GitHub 为准；报告不追述之后的变化。
- **替代解释**：「方案当交付」与「归属错位」也可能主要来自模型能力、提示词或界面设计，而不是缺少任务状态对象；作者本人在同一段里把可能的差距归于模型、提示词、工具、上下文和运行机制（`652.md:12`），报告没有排除这种解释。

## 对 Nuska 的意义

这批材料支持一个有限但有用的判断：作者要的不是单点功能，而是一条可追溯的「意图 → 派发 → 执行 → 验收」链路，其中最硬的两个失败是「方案当交付」和「归属错位」（`676.md:29`、`675.md:12`），二者都指向同一处缺失——没有任务级的状态与归属对象。这与 Nuska 的问题意识同向，但材料停在提案与自我限定上，不能作为效果证据。

以下五条是报告的归纳（H1–H5），不是原文主张；每条都能落回作者自己列的实验设计（`652.md:41`、`657.md:77-83`、`evaluation:23-30`、`context:44`）。

| 假设 | 依据 | 可测判据 |
| --- | --- | --- |
| H1 若系统不区分「方案」与「执行」，管理员会把方案当交付 | `676.md:29`、`676.md:35`、`synthesis:15` | 收到明确执行请求后是否出现实际派发与产物事件；错误完成声明数（`evaluation:17`） |
| H2 若任务归属只存在 Session 或提示词里，跨群与通知必然错位 | `675.md:17`、`675.md:29`、`643.md:12` | 同一任务在 Bot 视图、群视图与结果位置是否为同一份配置（`675.md:24`） |
| H3 若角色只写在 instructions 里，人设不产生能力或权限差异 | `657.md:94`、`639.md:36`、`650.md:49` | 两个人设 Bot 在同一任务上的工具、权限与验收差异 |
| H4 若完成判定只看「最终回复」，回合结束会被当成目标完成 | `656.md:23`、`656.md:43` | 部分完成、失败与取消被标为完成的比例（`evaluation:17`） |
| H5 上下文投递不等于采纳，目标修订后产物可能仍用旧版 | `context:42`、`context:38` | 修订后产物引用的目标版本、约束丢失率 |

对 Nuska 的直接意义有三点：把「谁对最终交付负责」做成可查询的对象，而不是提示词里的约定；把「完成」定义为逐条必要条件加独立检查，而不是回复结束或自报；把角色差异落到工具、权限与验收约束上，而不是名称。这些是候选设计方向，不是已实现的功能，也不构成对 DS Bot 现状的完整评价。界面类帖子（#638/#647/#648/#649/#661）提示了一个反面参照：侧栏组织、引用与表情互动可以被认真设计，但它们不改变交付链路；连接器与远程工作区（#639/#650）则说明权限与运行环境边界会直接限制这条链路能做到什么程度。
