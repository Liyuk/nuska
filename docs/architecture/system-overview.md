# Nuska 系统架构：初步研究假说

状态：讨论草案；不是已实现的接口或组件。

## 边界与依赖方向

交互入口收集人的请求和反馈；Nuska 候选能力负责理解目标与变化、推进工作、汇总证据；宿主接入层适配运行时能力；宿主提供实际模型、工具、会话及权限等能力。依赖应尽量指向清晰的宿主能力边界，但共享核心的大小和部署形式需由实验决定。

## 候选能力

| 能力 | 输入与输出（概念层） | 待验证问题 |
| --- | --- | --- |
| 意图 | 用户表达、上下文和反馈 → 目标、假设、约束及修订 | 如何识别隐含目的和错误假设？ |
| 工作推进 | 目标与当前状态 → 可执行的下一步、阻塞或结束 | 谁驱动执行，何时询问，如何避免重复调度？ |
| 任务记录 | 状态变化、用户修订、宿主事件 → 可恢复的任务历史 | 与宿主会话日志如何关联，恢复由谁负责？ |
| 证据与交付 | 产物、检查及人工判断 → 完成状态和剩余事项 | 哪些判断可自动化，怎样识别证据不充分？ |
| 可观测与交付 | 运行事件、阶段成果和用户介入 → 进度与结果证据 | 如何区分实际产物与模型声明？ |
| 宿主接入 | 版本、能力、生命周期与事件 → 明确支持范围 | 不支持启动、续跑、事件订阅时如何降级？ |

这不是六个必须独立实现的模块，也不是公共 API。一个初期实验可能只实现其中一小部分。

## 候选接入方式

1. **宿主内插件**：复用宿主生命周期与现有工具；受宿主接口和版本限制。
2. **宿主外服务**：通过公开协议或 API 控制宿主；隔离更清晰，但可能无法观察或控制所有状态。
3. **独立运行**：自主选择运行时，控制力更强，也需要自行处理调度和恢复。

同一宿主可能支持多种方式。选择前建立能力矩阵，记录可发起任务、持续运行、读取事件、工具与权限、持久化、恢复、取消和版本限制。

## 数据与运行边界

- 将原始用户表达、当前目标、目标修订、执行记录与检查证据分别建模；明确来源、时间和不确定性。
- 区分宿主事件和 Nuska 自身决定；定义任务与会话的关系，避免双方各自恢复导致重复执行。
- 对不可确认结果的外部操作，先核对状态再决定重试；记录幂等与恢复限制。
- 完成判断应区分自动检查、人工验收和未知；验证证据自身是否足以支持结论。
- 尊重宿主权限与用户授权，无法获取的权限和能力应报告，不通过假定或绕过实现。
- 限制敏感数据进入公开实验材料。

## 第一个架构实验

选一个真实交付任务，先记录当前宿主行为和人工负担，再增加一个最小能力（例如验收证据记录或目标修订跟踪）。对比完成质量与人工介入，并验证宿主重启和失败场景。必要时研究第二个宿主的公开扩展能力，判断共享边界是否真实存在。
