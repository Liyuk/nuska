# Nuska 项目总规划

状态：讨论草案 · 2026-10-29

## 1. 愿景与边界

Nuska 研究并逐步构建一种自主 Agent 体验：人用自然语言表达通常明确而强烈的目标，系统根据持续获得的新上下文自主调整路径，组织和推进工作，处理障碍，并交付可检查的阶段性成果与最终结果。项目将研究材料、真实任务和可运行原型联系起来，持续积累可公开的文章素材与工程证据。

预期减少用户拆解步骤、催促、维护上下文及发现遗漏的负担。自主程度不是无限制行动：涉及用户判断、授权、外部副作用或重要歧义时，需要清晰的边界和合适的介入点。

Grok Bot 是当前重要的体验参照，其是否代表最终形态保持开放。DeepSeek Harness、Pi、Hermes 和其他系统是研究与接入候选；目前没有选定底座、模型、语言或 UI。

## 2. 核心问题

1. **理解意图**：从不完整、口语化、不断变化的表达中推断目标、约束和成功条件；保持假设与事实的区别。
2. **适时交流**：区分可以合理推进的空白与必须询问的问题；支持随时纠偏，避免因过度询问把协调负担退回给用户。
3. **持续执行**：拆解与领取工作、调用能力、处理失败、恢复中断、识别停滞和合理停止。
4. **意图保持**：关联目标及其修订、执行轨迹、关键决策与记忆，避免长任务逐渐偏离。
5. **交付与验收**：把产物、完成情况、检查证据和未完成事项交给用户；区分机器可检验与需要人判断的要求。
6. **阶段性交付**：在任务推进中交付可用成果，并根据新信息更新下一阶段，不以反复确认代替执行。
7. **可移植性**：让经验证的能力有机会接入不同宿主，同时承认各宿主的能力和运行限制。

## 3. 用户体验与任务生命周期

这是候选模型，具体状态和接口需实验决定。

```text
表达愿望 → 理解和记录目标 → 自主行动与持续检查
    ↑               ↓                    ↓
补充 / 纠偏 ← 阶段性交付或必要时请求判断 ← 失败、歧义或边界
                                         ↓
                              交付产物、证据和未完成项
                                         ↓
                                 用户验收 / 继续修正
```

系统应能表达目标、重要假设、当前进展、阻塞、产物和依据；不要把“模型说完成”当作完成证据。不同任务有不同验收：文件存在可自动检查，观点和体验常需要人判断，未知项应保持未知。系统还需记录用户后续更正，并重新检查既有工作的适用性。

## 4. 研究与证据体系

详见 [研究地图](../research/index.md)。各方向不是预先认定的结论，而是研究问题：

- **产品与行为**：Grok Bot、DSBot 等产品的交互、任务领取、连续执行、恢复和交付体验。
- **人的意图与互动**：强目标表达、新信息、调整、信任与控制。
- **自主执行**：任务调度、记忆、上下文、工具、失败恢复与轨迹。
- **框架与生态**：DSH、Pi、Hermes 等的公开接口、扩展模式和适用条件。
- **结果与评估**：阶段成果、交付完整度、目标满足、可靠性和人力负担。

每份报告记录问题、资料及版本、方法、观察与证据、推断、反例、局限和下一步。将第一人称体验、公开资料、可复现观察和设计假设分别标识；不把模型自述当作外部事实，不从可见行为直接断言闭源系统的内部实现。

既有博客、工程工作流、harness 研究与 DSBot 的原始材料先建索引；能公开的摘要再引入，个人经历、会话和组织材料需要核对可分享范围。报告可以逐渐沉淀为博客，但研究档案保留不确定性与版本。

## 5. 工程架构方向

详见 [架构草案](architecture/system-overview.md)。候选分层：

```text
交互入口：对话 / CLI / 宿主 UI
           ↓
Nuska 能力：意图与修订 / 推进 / 恢复 / 证据与验收
           ↓
集成边界：宿主能力探测 / 事件映射 / 生命周期
           ↓
DSH 插件 / 其他框架扩展 / 可选独立运行
```

共享能力先由真实实验识别，不预设一定是库、服务或自己的 harness。宿主负责哪些能力、Nuska 拥有哪些状态与控制权、多个调度器如何避免冲突，都需要通过具体宿主验证。公共合同等至少一个可运行样例、并参考第二种宿主的实际需求后再稳定。

任务状态与会话记录、事件映射、重试幂等、副作用结果未知、暂停/恢复、预算、授权、日志与数据存储属于需要在接口边界解决的问题。宿主不支持某能力时，应暴露限制或停用对应功能，不伪装成完整支持。

## 6. 项目组织

详细目录见 [项目结构](project-structure.md)。单仓库先分别组织 `research/`、`cases/`、`experiments/`、架构文档，以及未来按需出现的共享包、集成和插件。多子项目暂不意味着多仓库；只在版本发布、所有权或维护边界确实独立时评估拆分。

- **研究**负责可追溯的结论和开放问题。
- **案例**定义输入、环境、期望结果及人工判断方式。
- **实验**记录配置、运行、结果和对照，区分协议与实际结果。
- **工程**实现经实验支持的能力，记录假设和宿主兼容范围。
- **插件**作为独立接入单元维护宿主依赖、生命周期和兼容性。

## 7. 对照与评估

以同一任务、尽可能一致的资源和输入比较产品或方案。记录模型及版本、工具权限、运行环境、执行次数、用户介入和时长。不能控制或观测的变量写明，不凭单次体验得出普遍排名。

候选指标：

- **目标与意图**：是否覆盖真实目的、是否发生未纠正的目标漂移、需要几次关键澄清。
- **完成与质量**：交付完整度、检查通过情况、可用性，以及人对结果的评价。
- **可靠性**：多次运行的完成比例、失败/停滞可见性、中断后的恢复情况。
- **用户负担**：需要催促、纠偏、拆任务或接管的次数与耗时。
- **阶段成果**：阶段性交付是否可用、能否支持下一步判断与调整。

指标定义、评分规则、样本数与置信限制必须在实验中单独说明；没有数据时只记录体验，不制造成功率数字。

## 8. 实施阶段

阶段是探索顺序，不承诺日期或已完成的功能；每一阶段可以依据证据调整。

| 阶段 | 核心产物 | 进入下一阶段的依据 |
| --- | --- | --- |
| 0. 建立基线 | 研究索引、可公开材料清单、若干真实任务及观察记录 | 至少一个具体场景有清晰目标、验收和可用证据 |
| 1. 体验与生态研究 | Grok Bot 行为观察、DSBot 问题汇总、候选框架能力矩阵 | 至少一个可复现的差距及可检验假设 |
| 2. 最小实验 | 选定一个任务，对照基线与候选改进，记录质量、介入和代价 | 有实际结果，能解释是否值得继续 |
| 3. 首个集成原型 | 在适合的宿主实现单一闭环，验证启动、推进、结果与失败 | 真实宿主和重启/失败情形有证据；局限清楚 |
| 4. 可移植能力 | 与第二种宿主比较，抽取被证明共享的边界和能力 | 至少两种接入方式支持同一明确任务，或清楚记录不可移植之处 |
| 5. 持续演进 | 多案例评估、版本管理、插件维护与公开成果 | 根据实际使用价值和结果质量决定下一步 |

首个宿主可以是 DSH，但必须根据其当前版本、扩展点和实际任务验证决定。Grok Bot 的体验值得学习；不预设其内部机制或克隆其产品实现。

## 9. 决策与尚未回答的问题

- **产品定位**：自主 Agent 到什么程度需要主动询问？哪些情境需要明确授权？
- **行为研究**：当前可使用的 Grok Bot 版本、环境和可复现任务是什么？
- **实现**：是宿主内插件、宿主外服务、库，还是多种形式？哪些能力真的可以共享？
- **状态**：意图、任务状态、证据和宿主日志如何关联，谁负责恢复与调度？
- **发布**：语言、许可、版本兼容、插件命名和后续是否拆仓。
- **素材**：哪些个人经历、现有项目和运行记录能够公开，哪些需要抽象或留在本地。

重要决定写入 `docs/decisions/`，记录背景、选项、证据、后果与复审条件。以上问题目前均未预先定案。
