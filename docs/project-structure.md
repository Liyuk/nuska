# Nuska 项目结构与研究计划

状态：讨论草案 · 2026-10-29

## 项目目标

研究和构建一种从用户意图到可验证交付的自主 Agent 体验。用户通常从强目标出发，随着新信息补充上下文或调整方向；系统应自主持续执行，交付阶段性成果并以证据支持结果验收。Grok Bot 是体验参照，具体实现与内部机制有待研究；框架、语言和运行方式尚未选定。

项目同时承载研究、案例、可重复实验、工程原型和框架集成。起步阶段采用一个仓库，成熟后仅在发布、维护或权限边界确有需要时考虑拆分。

│   ├── intent/               意图表达、澄清与漂移
│   ├── execution/            自主运行、恢复与记忆

## 可能的系统边界

```text
用户意图 / 反馈
        ↓
Nuska 候选能力：意图记录与修订 · 任务推进 · 证据与验收
        ↓
宿主适配：能力探测 · 事件和状态映射 · 调用/恢复
        ↓
DSH 插件 / 其他宿主扩展 / 独立运行（按实际支持选择）
```

- **共享能力候选**：任务目标及其修订、推进与停滞、证据和完成判断、用户介入记录。先根据实验确定哪些逻辑值得共享；不假设一定需要单独调度器或统一运行时。
- **适配层**：描述宿主能提供什么、如何发起和恢复工作、如何获取事件。不同框架接口差异可能需要进程内插件、外部服务或仅支持部分功能；无法支持的能力须明确报告。
- **宿主插件**：处理注册、宿主生命周期和配置。候选的 DSH 插件需对照公开接口与实际版本验证；不把 DSH 的事件或内部类型直接当成跨框架合同。
- **状态与控制权**：任务状态和宿主会话日志的对应、去重、重启恢复、谁有权继续任务、冲突及副作用处理都是待实验问题。宿主已有目标机制时先研究复用，避免重复调度。
- **接口策略**：先比较一个真实场景和至少两个不同宿主的实际能力，再稳定公共接口；若暂时只有一个宿主，保留内部边界，不宣称已跨框架。

## 研究报告地图

| 方向 | 首批问题与产物 | 状态 |
| --- | --- | --- |
| 体验基线 | 对照 Grok Bot、DSBot 等真实任务：用户给了什么，系统做了什么，在哪些地方接管 | 待整理案例 |
| Grok Bot 行为研究 | 在可访问的产品表面观察任务领取、持续执行、交付、失败与恢复；记录版本与环境 | 待建立协议 |
| Harness 与集成 | 比较 DSH、Pi、Hermes 等公开扩展点、持久化、恢复和权限能力 | 待核验 |
| 意图形成 | 识别模糊目标、合理假设、澄清时机、后续更正和目标漂移 | 待研究 |
| 独立执行 | 对比委派、任务领取、调度、停滞检测、恢复与预算 | 待研究 |
| 交付与验收 | 产物存在、可执行检查、人工判断与用户原始目的是否一致 | 待设计实验 |
| 阶段性交付 | 研究阶段成果是否可用，如何反馈并支持目标调整 | 待设计实验 |

每篇报告尽量记录研究问题、材料与版本、观察方法、证据链接、结论与置信度、反例及未解决问题。区分**观察到的行为**、**推测的内部机制**和**自己的设计方案**；不把产品体验推断成已证实的内部架构。

## Grok Bot 研究方法

1. 先确认研究对象、可访问的产品版本和可用材料，保留当时的使用条件。
2. 选择用户真实关心的任务，记录原始目标、后续补充、可见进展、阶段成果、产物和用户介入。
3. 在条件允许时复跑可控任务，改变歧义程度、任务长度、失败条件和执行预算；记录失败与无法观察的部分。
4. 将观察归纳为可验证的行为要求和假设，再用独立实现或可用扩展实现比较；不声称仅从界面推断出内部源码、提示词或调度机制。
5. 如后续要分析用户提供的客户端或其他实际产物，单独确认目标、版本、可用分析方式与范围，保留证据和局限。

## 现有素材入口

- DSBot 是外部参考项目；已有的个人反馈和本地研究材料用于研究任务推进、交付差距和验收。公开引用时区分个人观点、项目实际实现和原作者归属。
- Graph Memory 与 DSH Mnemon 也是外部参考项目；可以研究其记忆与上下文实现，不将它们归为自己的项目。
- DeepSeek Harness 的官方仓库和本地插件实验可用于研究公开扩展点、事件和版本兼容性；已有能力不等于已验证适配。
- 已有 harness 对比、工程工作流研究与博客可按主题交叉链接；保留各自原始仓库的用途，避免盲目复制。
- 用户的口述、公司经历、聊天记录、截图及其他可能含个人或组织信息的材料先保存在本地，公开前整理和核对可分享范围。

## 第一轮推进

1. 建立研究索引：梳理已有博客、DSBot 需求与实验、Grok Bot 的真实使用案例；对每份材料标明位置、状态和是否可公开。
2. 选一个端到端任务，写清初始愿望、可观察结果、预期验收和允许的用户介入；记录 Grok Bot 与可用替代方案的实际表现。
3. 调研 DSH 当前版本的目标、生命周期与插件扩展点，确认可否实现该任务所需的继续执行、事件观察和结果检查；记录缺口和限制。
4. 依据实测选一个最小原型：先验证一个具体能力和宿主接入，再决定是否抽出共享核心和扩展第二个宿主。
5. 把实验结论、失败与未解决问题写回研究索引；持续积累可公开的博客素材与项目证据。

## 待决定

- 首个典型任务及它的验收方式；哪些能力最能解释 Grok Bot 的体验。
- 深度研究基于哪些实际可访问材料，是否存在可重复、可比较的实验条件。
- DSH 的现有目标驱动功能与 DSBot 能否复用、需要何种扩展；是否选择其他首个宿主。
- 宿主内插件与宿主外运行服务各自的能力和限制。
- 语言、许可证、版本策略以及何时公开发布插件或拆分子项目。
